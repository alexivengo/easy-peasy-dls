# Easy Peasy DLS v0.10.0 — UI/UX и Architecture Decisions

## Результат

Сделать UI/UX-источник и архитектурные решения полноценными, но лёгкими
частями DLS lifecycle.

После изменений:

- UI change не проходит definition gate без типизированного design source либо
  явного human-approved bypass;
- Tier 1 не требует искусственного макета, если существует точный precedent;
- Tier 2 и Tier 3 используют версионированный design source, а не ссылку без
  зафиксированной версии;
- architecture approval требуется только при явном architecture trigger или
  ADR, а не для каждого standard/critical change;
- изменение несвязанной части SPEC не инвалидирует неизменившиеся design и
  architecture approvals;
- пользователь подтверждает смысловые решения, а DLS автоматически ведёт
  digests, staleness, context, ReviewPack и Delivery Receipt;
- Figma, Sketch и другие connectors не становятся обязательными и не входят в
  этот релиз;
- review-алгоритм, модели и default budgets не меняются без данных реальных
  pilots.

Версия: `v0.10.0`.

State schema остаётся v1, ReviewPack/ReviewIR — v2. Исторические approvals и
artifacts остаются читаемыми без миграции.

## 1. Typed design-source contract

Добавить в change state необязательный DLS-owned контракт
`dls-design-source/v1`:

```json
{
  "contract": "dls-design-source/v1",
  "tier": 2,
  "surfaces": ["settings", "authentication"],
  "mode": "source",
  "source": {
    "kind": "artifact",
    "ref": "docs/design/EPIC-05b-auth-settings.md",
    "version": "git:0123456789ab",
    "content_digest": "sha256:...",
    "git_blob": "..."
  },
  "bypass": null
}
```

Для явного решения работать без макета:

```json
{
  "contract": "dls-design-source/v1",
  "tier": 3,
  "surfaces": ["authentication"],
  "mode": "bypass",
  "source": null,
  "bypass": {
    "rationale": "...",
    "ux_risk": "high"
  }
}
```

### Tier policy

- Tier 1: допускается точный существующий precedent. Новый макет не требуется,
  если явно названы переиспользуемые surface и precedent.
- Tier 2: требуется versioned artifact, exact precedent либо внешняя версия,
  которая однозначно фиксирует рассматриваемый UX.
- Tier 3: по умолчанию требуется immutable design artifact. Human-approved
  bypass остаётся допустимым, но обязан содержать rationale и явный `ux_risk`.
- DLS не делает Figma, Sketch или конкретный формат обязательными. Источником
  может быть repository artifact, exact product precedent либо версионированная
  внешняя ссылка.

### Integrity rules

- Repository-local source должен быть repository-relative, tracked и привязан
  к exact Git blob/content digest.
- Запрещены absolute paths, traversal, symlink escape и ссылки вне Git
  common-dir.
- External source должен использовать HTTPS и иметь явную immutable version.
  DLS не загружает внешний контент и не объявляет URL immutable без версии.
- Raw design content, binary assets, credentials и абсолютные локальные пути не
  попадают в state telemetry, metrics или model-facing status payload.
- Изменение source, version, surfaces, tier или bypass создаёт новый design
  digest и инвалидирует соответствующий approval.

## 2. Низкоуровневый CLI

Добавить команды, которые workflow skill вызывает автоматически:

```text
dls design set CHANGE_ID \
  --tier 1|2|3 \
  --surface SURFACE [...] \
  --source-kind precedent|artifact|external-version \
  --source-ref REF \
  [--source-version VERSION] \
  [--risk low|medium|high] \
  [--operation-id ID] \
  [--dry-run]

dls design set CHANGE_ID \
  --tier 1|2|3 \
  --surface SURFACE [...] \
  --bypass \
  --rationale TEXT \
  --risk low|medium|high \
  [--operation-id ID] \
  [--dry-run]

dls design status CHANGE_ID
```

Расширить approval-flow:

```text
dls approve CHANGE_ID \
  --decision definition \
  [--include-design] \
  [--operation-id ID] \
  [--dry-run]
```

`--include-design` атомарно записывает два независимых approvals из одного
scoped human confirmation: definition и design. Standalone
`approve --decision design` сохраняется для раннего решения, legacy packages и
диагностики.

Пользователь не вводит эти команды в обычном процессе. Skill переводит
естественный ответ пользователя в bounded CLI mutation.

## 3. Scoped approval digests

Ввести два производных контракта:

- `dls-design-digest/v1` — tier, surfaces, source/bypass contract и immutable
  provenance;
- `dls-architecture-digest/v1` — только authored architecture decision и ADR,
  если он существует.

Правила staleness:

- definition approval остаётся привязан к полному authored definition digest;
- design approval привязан только к design digest;
- architecture approval привязан только к architecture digest;
- изменение design или architecture также инвалидирует definition approval,
  потому что меняет продуктовый контракт;
- изменение несвязанной части SPEC инвалидирует definition approval, но не
  делает неизменившиеся design/architecture decisions неподтверждёнными;
- execution metadata, tickets status, findings, evidence и generated regions не
  входят ни в один decision digest;
- legacy approvals без scoped marker читаются по прежнему whole-definition
  правилу и не переписываются автоматически.

Обновить approval schema и state validation необязательными полями:

```json
{
  "decision_contract": "dls-design-digest/v1",
  "decision_digest": "..."
}
```

Существующие поля approval сохраняются для обратной совместимости.

## 4. Architecture decision lifecycle

Architecture approval становится обязательным только если:

- change содержит impact tag `architecture`; либо
- package содержит canonical ADR artifact.

Другие high-risk signals могут заставить skill рекомендовать architecture
decision, но не создают скрытый hard gate сами по себе.

### Canonical source

Приоритет источника:

1. canonical ADR artifact;
2. bounded architecture region в SPEC.

Обновить SPEC template:

```markdown
<!-- dls:architecture:start -->
## Architecture and alternatives

...
<!-- dls:architecture:end -->
```

Для adopted packages поддержать deterministic legacy headings:

- `## Architecture`;
- `## Architecture and alternatives`.

Если регион отсутствует или найдено несколько неоднозначных кандидатов, DLS
возвращает typed action `record-architecture-decision` и не угадывает текст.

### Lifecycle

1. При раннем critical architecture trigger агент формулирует bounded decision
   и alternatives до завершения SPEC.
2. Пользователь отдельно подтверждает architecture decision.
3. Агент завершает остальную SPEC и definition review.
4. Пользователь подтверждает definition.
5. Если отдельный ранний trigger отсутствует, architecture остаётся частью
   обычного definition review и отдельный approval не создаётся.

ADR остаётся опциональным. DLS не требует отдельный файл, если решение полно и
однозначно зафиксировано в SPEC.

## 5. Gates и typed actions

Общий readiness resolver должен использовать один и тот же design/architecture
status для `check`, `context`, `candidate-ready`, `review-run`, status-команд и
Delivery Receipt.

Добавить typed actions:

- `record-design-source`;
- `approve-design`;
- `approve-definition-and-design`;
- `record-architecture-decision`;
- `approve-architecture`.

Правила:

- UI change без design source/bypass останавливается до implementation context;
- записанный, но не подтверждённый source возвращает `approve-design`;
- готовые definition и design могут вернуть один
  `approve-definition-and-design`;
- architecture-triggered change без решения возвращает
  `record-architecture-decision`;
- решение без current approval возвращает `approve-architecture`;
- ни один из этих blockers не запускает validation или model review;
- structural PASS не считается human approval.

## 6. Context, ReviewPack и review

Добавить в generated context manifest и новые ReviewPack v2 необязательную
bounded projection:

```json
{
  "decisions": {
    "design": {
      "contract": "dls-design-source/v1",
      "tier": 2,
      "surfaces": ["settings"],
      "mode": "source",
      "source_kind": "artifact",
      "digest": "...",
      "approval": "current"
    },
    "architecture": {
      "required": true,
      "source_kind": "adr",
      "digest": "...",
      "approval": "current",
      "triggers": ["architecture"]
    }
  }
}
```

Проекция не содержит raw binary, полный design document, absolute paths,
credentials или внешний контент.

Review использует existing UX risk lens и platform-profile routing. Новый
обязательный specialist, model, effort, budget или approval не добавляется.
Design/architecture provenance помогает reviewer проверить соответствие
реализации подтверждённому решению, но не подменяет code review.

## 7. Delivery Receipt и telemetry

Delivery Receipt показывает отдельно:

- design tier;
- source kind либо explicit bypass;
- surfaces;
- design approval status;
- architecture required/source/approval status;
- оставшуюся human boundary.

Receipt не включает raw design content и не превращает наличие source в
review-clear, acceptance, release или production readiness.

`review-metrics` получает только безопасные aggregates:

- UI tier;
- source kind;
- bypass boolean;
- architecture required boolean;
- platform profile;
- context bytes/words/input count;
- existing lane/model usage.

Source ref, content, rationale, credentials и локальные paths в metrics не
попадают.

## 8. Workflow skill UX

Обновить **Easy Peasy DLS: процесс**:

- при `user-interface` skill рекомендует tier на основании scope и platform
  profile;
- вопрос пользователю задаётся только когда не определён source или решение о
  bypass;
- Tier 1 не провоцирует создание лишнего макета, если найден exact precedent;
- standard/critical flow по умолчанию просит одно совмещённое подтверждение
  design + definition после semantic definition review;
- routine UI change получает одно design confirmation, без искусственного
  epic/ADR;
- отдельное architecture confirmation появляется только при раннем critical
  trigger;
- пользователь не копирует digests, paths, design IDs или CLI-команды;
- skill не создаёт bookkeeping subagent и не пересказывает design source в
  каждой implementation/review задаче;
- после approval implementation получает compact decision projection через
  context manifest.

- design edit stale design и definition approvals;
- atomic definition + design approval и idempotent retry;

### Architecture

- impact `architecture` требует bounded decision и approval;
- ADR требует architecture approval;
- обычный critical change без trigger не получает искусственный gate;
- SPEC marker extraction;
- adopted legacy heading extraction;
- missing и ambiguous region;
- deterministic architecture digest;
- unrelated SPEC edit не stale architecture approval;
- architecture/ADR edit stale architecture и definition approvals;
- no mandatory ADR when SPEC region is sufficient;
- legacy whole-definition architecture approval remains readable.

### Orchestration и privacy

- candidate/review блокируются до model calls при unresolved decision;
- `check`, `context`, candidate/review/delivery status возвращают одинаковый
  typed action;
- ReviewPack содержит bounded decision projection;
- Delivery Receipt корректно разделяет design/architecture/review/acceptance;
- metrics не содержат refs, raw content или absolute paths;
- payload limits сохраняются;
- fake-Codex routine/standard/critical paths не добавляют лишних lanes;
- skill forward-test подтверждает отсутствие обязательного Figma/Sketch,
  ручных CLI-шагов, repeated approval и bookkeeping subagents;
- state v1 и ReviewPack/ReviewIR v1/v2 без decision markers читаются.

## Зафиксированные решения

- UI/UX source обязателен для UI changes, но конкретный design tool — нет.
- Явный human-approved no-mockup bypass остаётся доступным для всех tiers и
  обязан фиксировать UX risk.
- Tier 1 не требует лишнего макета при точном precedent.
- Design и architecture approvals получают scoped digests.
- Значимое изменение design или architecture инвалидирует definition approval;
  несвязанное изменение SPEC не стирает сами decision approvals.
- Architecture approval появляется только при explicit trigger/ADR.
- ADR не становится обязательным документом.
- Review-алгоритм, models и default budgets в v0.10.0 не меняются.
- A01/A02 connectors и автоматическая внешняя provenance остаются следующей
  Attractive-волной после реального UI pilot.
- Пользователь подтверждает решения, а DLS автоматизирует bookkeeping,
  staleness, context и traceability.
- Реализация выполняется только в `easy-peasy-dls`; `my-ai-dls` остаётся
  неизменяемым R&D-архивом.
